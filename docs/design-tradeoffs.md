# 设计取舍说明

篇幅约束：两页以内。只回答三个问题：为什么把解析与执行隔离、如何避免误操作、没有实现什么。

## 一、为什么把解析与执行隔离

**约束**：自然语言输出不可信。模型可能给出未知操作、多余字段、负数时长、越界源区间，甚至被工序内文本诱导。同时用户需要可预测的确定性结果。

**做法**：解析器（离线句式或模型）只能产出一份 `ParseResult`，其中操作是受注册表约束的数据结构；执行引擎不接受文本、不接受代码、不接受表达式，只接受 `[]Operation`，并且：

- 字段白名单在解码阶段生效（`Operation.UnmarshalJSON`），未知字段、null、未知类型直接拒绝；
- 每个操作在执行前检查前置条件（存在、未锁、类型、时间），执行后检查局部不变量；
- 整批结束后统一校验重叠与全局唯一性；
- 模型输出还要过 `validateParseResult`：状态与载荷必须匹配（`answer` 不能带操作，`clarify` 的候选必须真实存在）。

**代价**：解析与执行之间多一层数据契约，新增操作必须同时改注册表、句式、提示词与测试，不能"只改一处"。我们接受这个代价，因为它换来一条硬性质：**无论模型说什么，能落到时间轴上的只有这五类操作**。

**什么信号出现时改**：如果出现第二类执行端（例如真实渲染管线），才需要把 `Project` 抽象成接口；在只有一种执行端时引入接口只会增加转译层。

## 二、如何避免误操作

按"越靠前越便宜"排列，共五层：

| 层 | 机制 | 拦住什么 | 代价 |
| --- | --- | --- | --- |
| 1 | 解析阶段不猜：目标多候选一律 `clarify`，并列候选 ID | 改错片段 | 多一轮交互；离线句式覆盖不全时只能拒绝 |
| 2 | 计划只存操作与绑定，预览由引擎真实计算 | 预览与实际不一致 | 确认时需要重算一遍（毫秒级） |
| 3 | 计划绑定 `project_id + revision + epoch` | 看完预览后工程变了仍然提交 | 重新导入即失效，用户要重来一次 |
| 4 | 整批原子提交，失败零修改 | 一半改了一半没改 | 批次内无法表达"尽力而为"，需要用户拆指令 |
| 5 | 撤销用快照恢复，且版本继续递增 | 撤销后状态错乱、版本回退引发缓存问题 | 内存占用随步数增长，上限 100 步 |

两处特意放宽的地方：

- **批次内允许临时重叠**：交换两段顺序必须经过重叠瞬间，因此只在提交前校验重叠。放宽的是中间态，提交态仍然严格，原子性不受影响。
- **删除只要求确认，不要求二次口令**：预览卡片会明确标注"将删除此片段"，并提示可撤销。再加一层确认会降低正常编辑效率，收益不足以抵消。

**代价总体是"多一次确认"**。我们选择承担它，因为剪辑误删的时间成本远高于点一次按钮。

## 三、没有实现什么

| 未实现 | 原因 | 若要做，代价是什么 |
| --- | --- | --- |
| 视频编码导出 | 任务明确不做，且需要 FFmpeg 与时间基转换 | 引入外部二进制依赖与大量格式兼容问题 |
| 波纹推移（自动后移后续片段） | 会让"移动一段"变成"改动全轨"，风险与可预测性冲突 | 需要重新定义碰撞语义与预览粒度 |
| 持久化工程 | 任务允许"重启前持续工作"，内存实现足以验收 | 需要事务、并发写、迁移；撤销栈也要落盘 |
| 多人协作 / 权限 | 本地单人工具，无服务端身份体系 | 需要鉴权、锁、冲突合并 |
| 指令内部的单步撤销 | 撤销单位是整条指令，语义更清晰 | 需要把快照改成操作级日志 |
| 画面异常检测、自动字幕、降噪 | 属媒体处理而非时间轴编辑 | 需要视觉模型与转码链路 |
| 任意自然语言 | 离线只支持固定句式，自由表达需配模型 | 模型接入后仍需人工确认，收益有限 |

另有两条**主动放弃**的扩展，原因相同——不服务验收目标：

- **产品化 v1 HTTP 接口**（多工程、身份、条件写入）：任务书未要求，且会让本地演示路径与产品路径产生两套语义。已移除。
- **前端可视化框架**：原生模块足以支撑当前交互，引入框架会增加构建链与审查面。

**未做不等于不能做。** 每一条的触发条件都写在设计文档与范围声明里：出现真实渲染管线、真实多人使用、真实持久化需求时再引入，且引入时必须先补对应的失败语义测试。
